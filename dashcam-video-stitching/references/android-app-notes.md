# 把拼接做成 Android APP：技术路线与成本

用户常问"包一层 ffmpeg 做个 APP 难吗"。结论：**不难，但不要真的包 ffmpeg**。成本不在拼接逻辑，在手机端的解码/合成/编码性能。

## 性能现实

一条 1:45 的 4 路 4K HEVC 素材：

| 方案 | 手机端耗时 | 备注 |
|---|---|---|
| ffmpeg 软解 + libx265 软编 | 数十分钟 ~ 数小时 | 会发热降频、被系统杀掉；不可用 |
| MediaCodec 硬解 + GL 合成 + 硬编 | 几十秒 ~ 2 分钟 | 可用 |

ffmpeg-kit 已于 2025 年停止维护，二进制体积也大（full 包 100MB+）。把它塞进 APK 只为跑一条 `xstack`，性价比极低。

## 推荐架构（全原生，不需要 ffmpeg）

```
MediaCodec 硬解 × 4  ──►  4 × SurfaceTexture(OES)
                              │
                     OpenGL ES 画布（按模板摆位）
                              │
                 ──►  MediaCodec 编码器 input Surface（零拷贝）
                              │
                      MediaMuxer → MP4
```

要点：

1. **解码**：为每路创建 `MediaCodec` 解码器并绑定 `Surface`，用 `SurfaceTexture` 把画面变成 GL 纹理。
2. **合成**：`GLSurfaceView`/自定义 EGL 环境里画四个四边形，坐标就是 `xstack` 的 `layout`。模板做成常量表即可。
3. **编码**：`MediaCodec.createInputSurface()` 拿编码器输入 Surface，把 GL 直接渲染进去，避免读回内存（读回一次 4K 帧就是 10MB 拷贝，30fps 撑不住）。
4. **封装**：`MediaMuxer` 写 H.264/H.265 MP4，注意 pts 从 0 开始。
5. **同步**：四路按 pts 取帧，允许 1–2 帧容差；某路提前结束时补最后一帧。

## 机型坑

- **并发解码实例数**：部分机型只允许 2 个 4K 解码实例同时存在，4 路会失败。需要探测 `MediaCodecList` 能力并做降级（先解到较低分辨率、或分两批解码后缓存）。
- **解码器不支持非标准分辨率**：见 `compatibility.md`。侧视角通常 1280×1000 没问题，主视角若本身是 3840×1696 也没问题，问题是**合成后的画布**——但硬编时可以直接编码 3840×2696（编码器上限通常比解码宽松），真正要小心的是**播放**。
- **GL 纹理尺寸上限**：多数 GPU `GL_MAX_TEXTURE_SIZE` ≥ 4096，画布 3840×2696 安全。

## 产品逻辑（比技术更容易做对）

- **文件命名即索引**：`<品牌>_<视角>_YYYY_MM_DD_HH_MM_SS_mmm.mp4` 里的时间戳是天然主键，按它 group by 就能把同一次录制的多路聚合成一条。
- 用 `MediaStore` 查询视频，解析文件名取时间戳 + 视角，聚合后以"时间 + 时长"卡片展示。
- 模板固定几种即可（主上/三下、2×2、主+右侧竖排），不要做自由拖拽——那会把 UI 复杂度翻 5 倍，而用户实际只用一两种。

## 工作量估算

有 Android 基础的前提下：

| 范围 | 人日 |
|---|---|
| MVP：固定模板合成 + 相册聚合 + 进度/取消 + 保存 | 5–8 人日 |
| 可长期用：机型适配、后台任务、失败重试、大文件 OOM | +10~15 人日 |

## 验收要点

- 同一素材，APP 产出与桌面 ffmpeg 版本逐帧对比（时间轴偏移 ≤1 帧）
- 4K 素材在低端机上不崩、不 OOM
- 拼接点无黑帧、无跳帧

## 实测记录（供后来者少踩坑）

参考实现：一台 2019 年的 Kirin 980 机型（Android 10，8GB），输入 4 路 3840×1696 + 3×1280×1000，输出 105 秒。

| 指标 | 实测 |
|---|---|
| 端到端耗时 | 76 秒（约 1.4× 实时） |
| 编码器尺寸上限 | 高 2160，理想画布 3840×2696 被拒 → 自动缩到 3076×2160 |
| 输出码率 | 目标 70MB → 实际 63MB（编码器比请求值高约 10%，预留 18% 余量刚好） |

### 三个必须实现的细节

1. **喂帧节奏**：解码器永远比渲染快，`SurfaceTexture` 只保留最新帧。
   用"在途帧数 = 喂入数 − 消费数 ≤ 2"控制喂入（消费一帧才喂一帧），否则一段 20 秒的片子会丢掉近一半帧。
   只按时间戳节流不行：解码器有 1 帧输出延迟，喂不够就死等；喂多了就突发丢帧，实测很敏感。

2. **CFR 补齐**：即使节奏对了，偶尔还是会丢 1 帧。按内容 PTS 的跳变量计算应输出几帧
   （跳 2 帧就输出 2 次同一张），保证输出严格 30fps、总时长与源一致，而不是变短。

3. **结尾补帧**：EOS 时解码器会把缓冲的帧一次性吐出，`SurfaceTexture` 只留下最后一帧。
   循环结束后按"最后一帧 PTS + 1 帧"补齐，否则末尾会少 0.3–0.5 秒——取证片段往往就在结尾。

### 其它

- `MediaCodec.setParameters(KEY_VIDEO_BITRATE)` 在 Kirin 上可用，用来在末尾 15 秒提码率，不需要重启编码器。
- `codec.createDecoderByType()` 失败（并发实例不够）时，遍历 `MediaCodecList` 找 `!isHardwareAccelerated()` 的解码器兜底。
- 编码器输入是 Surface，PTS 用 `eglPresentationTimeANDROID` 设置；部分硬件编码器会按帧率重新计时，所以"帧数"才决定最终时长。

### 目标体积：三个容易翻车的点

移动端没有两遍编码，只能用「推码率 + 事后校验」，实测这三个坑必踩：

1. **硬件编码器有码率下限**。目标 8MB / 105 秒时算出来 500kbps，编码器实际吐 20MB（+145%）。
   解法：设一个"每像素码率"下限（如 0.008 bpp），低于它就别硬压，改为**降低输出分辨率**——
   同一次实测：3076×2160@500kbps 出 20MB；降到 1722×1208 后出 7.7MB，目标达成。
2. **给取证段提码率会抬高总码率**。目标很小时（均摊码率 <900kbps）应自动取消末尾提码率，
   否则提的那一段会把总量顶上去。
3. **留 15~18% 余量**。编码器实际输出普遍比请求值高 10%，按 0.82 的系数算目标码率，实测 70MB 目标出 63MB。

### 失败路径必须显式记账

`MediaCodec` 的编码器出错是"异步"的：`onError`、muxer 写失败、`signalEndOfInputStream` 后迟迟没有 EOS，
都不会让 `run()` 抛异常。不记账的话，UI 会把 0 字节/截断的文件标成"拼接完成"。
必须统计：`mEncoderError`、`mMuxerStarted`、`mSamplesWritten`、`renderedFrames`，任一不满足就报失败并删半成品。

另外：进程被杀会留下**不在 MediaStore 里的孤儿文件**（行已回滚、文件还在，且没有 moov）。
清理时不能只查 `IS_PENDING=1`（那时行已经没了），要扫目录 + 对比 MediaStore 记录；注意 targetSdk 29
在 Android 10 上默认是分区存储，**File API 列不出 /sdcard 目录**，需要 `requestLegacyExternalStorage="true"`。
